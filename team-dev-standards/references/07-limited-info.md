# 07 有限信息下的自主决策

## 1. 触发条件

满足任一条件时启用：

- 用户要求开发软件、功能或系统。
- 用户提供的信息不足以直接实现或验收。
- 需要 Agent 自主判断、设计、选型或推进。
- 需要查询竞品、相似项目、开源项目作为参考。
- 涉及高风险、不可逆、合规或生产操作。
- 需要在无人管控或开放式目标下持续决策。

## 2. 核心原则

1. 信息不足是常态；不能等信息齐全再行动。
2. "足够"是可操作定义，不是感觉（`§4`）。
3. 显式化不确定性：已知、未知、假设、冲突、待确认、置信度必须记录。
4. 先低成本信息源，后问人，最后外部调研（`§5`）。
5. 问用户要少而精：只问高价值、无法自取、必须用户拍板的问题。
6. 参考不照抄；对比后裁剪（`§7`）。
7. 关键风险必须人工审核（`02-safety-and-review.md §2`）。
8. 自主决策分级（`03-risk-and-autonomy.md §2`）。
9. 无验证的自主决策等于盲跑（`08-verification-and-retro.md`）。
10. 失误是常态，目标是让失误更便宜、更早暴露、更可逆、可学习（`09-execution-protocols.md §2`）。

## 3. 需求状态表

### 3.1 表结构

Agent 必须维护：

| 类别 | 内容 | 优先级 | 状态 | 影响 | 负责人 |
|---|---|---|---|---|---|
| 已知 | 用户明确说过的 | 高/中/低 | 已确认 |  |  |
| 未知 | 尚未获得的信息 |  | 待获取 |  |  |
| 假设 | Agent 暂时替用户定的 |  | 待确认 |  |  |
| 冲突 | 前后不一致或与约束冲突 |  | 待裁决 |  |  |
| 待确认 | 需要用户拍板 |  | 待审批 |  |  |
| 范围外 | 明确不做 |  | 已确认 |  |  |

### 3.2 优先级定义

- **阻塞实现**：不知道无法开发。
- **影响架构**：猜错会返工。
- **影响体验**：影响验收和用户流程。
- **可后置**：文案、样式、非关键排序。

### 3.3 刷新时机

- 每次 draft 前刷新一次；用户回答后立即更新。
- 每个阶段门（`§6.4`）结束前，假设项必须转为"已确认"或"已拒绝"。
- 会话结束把未决项写进 Handoff（`assets/handoff-template.md`）。
- 状态表与 `docs/STATE.md` 分工：状态表管"需求是否明确"，`STATE.md` 管"工程进展到哪"（`05-state-and-harness.md §1`）。

## 4. "足够"标准

信息足够，当且仅当能写出：

- 需求草案。
- 范围外清单。
- Given-When-Then 验收用例。
- 接口/数据草案。
- 关键假设与风险清单。

且：

- 高影响不确定项已解决，或已变为经用户批准的假设。
- 有下一步验证或实施计划。
- 用户已审批当前基线。

**如果写不出验收用例，说明信息不够。**

## 5. 信息优先级与收集顺序

### 5.1 优先级与信息源顺序

优先级公式：

> **信息优先级 = 决策影响 × 不确定性 ÷ 获取成本**

信息源顺序（先内后外、先静后动、先自动后人工、先证据后猜测）：

1. 现有代码与配置。
2. 现有文档与历史记录。
3. 运行中的系统与数据。
4. 自动探测与工具。
5. 原型、spike、mock。
6. 问用户。
7. 外部调研（`§7`）。

### 5.2 提问策略

- 一次问 3–5 个高价值问题，问完就出 draft，不挤牙膏（`09-execution-protocols.md §3.4`）。
- 给选项和推荐，不问开放式作文。
- 问决策题，不问信息题。
- 问"为什么""怎样算成功""失败会怎样"。
- 用具体场景反推边界。
- 对不知道的用户，给默认方案 + 风险说明。

### 5.3 必须主动收集

- 异常与边界：空数据、重复、权限、网络、并发、幂等、回滚、审计。
- 非功能需求：性能、安全、可用性、可观测、可维护、成本、合规。

## 6. Draft 与审批

信息有限时，必须生成 draft，而不是无限提问。

### 6.1 三层 Draft

1. **需求理解 draft**：目标、用户、核心场景、范围、不做什么、成功标准、已知/未知/假设。
2. **方案 draft**：总体方案、关键模块、数据流/接口草案、技术约束、备选方案、风险。
3. **执行 plan draft**：阶段、里程碑、待确认问题、验证动作、审批门、可逆性说明。

信息越少，越优先第一、二层；第三层可粗。

### 6.2 Draft 必含内容

见 `assets/draft-template.md`。

### 6.3 审批的是什么

- 目标理解是否正确。
- 范围边界是否可接受。
- 关键假设是否成立。
- 推荐方向是否继续。
- 是否允许进入下一阶段。
- 下一阶段是调研、原型还是正式实现。
- 哪些未知需用户拍板，哪些可由 Agent 默认。

**审批不是需求冻结，而是阶段门。**

### 6.4 审批闭环

draft → 审批 → 迭代 → 基线 → 再收集 → 再审批。

- 审批后不停止收集；发现新信息触发 draft 更新。
- 变更成本显式记录。
- 避免锚定：draft 必须给出备选与"不推荐"。
- 避免把假设当事实：假设必须标注状态。

### 6.5 决策卡（问用户时用）

```text
决策点 <编号>：<一句话问题>
- 选项 A：<...> ｜ 代价：<...> ｜ 推荐理由：<...>
- 选项 B：<...> ｜ 代价：<...>
- 默认（不回复时采用）：<A 或 B>，风险：<...>
- 影响面：<谁/哪个模块会受影响>
```

一次给 3–5 张卡，每张必须有默认项与代价，否则问题不成立。

## 7. 参考项目与对比评估

### 7.1 何时使用 searchtool

当信息有限、需要出 draft 或校准方案时，应查询：

- 同类竞品
- 局部功能相似产品
- 相反产品
- 成功开源项目
- 失败/反面案例
- 标准、协议、行业实践

### 7.2 参考分类与边界

| 类型 | 作用 |
|---|---|
| 同类竞品 | 功能范围、交互、商业模式、合规方式 |
| 局部相似 | 接口设计、插件体系、源管理、缓存、回退 |
| 相反产品 | 为什么不做某设计，是否必要 |
| 失败/反面 | 法律、运维、生态治理、滥用风险 |

参考什么：架构模式、接口协议、数据模型、边界处理、失败模式、演进路径、合规策略、运维方式。

不参考什么：具体代码、受许可证限制的实现、灰色版权源解析、与当前目标不匹配的复杂设计、过时或废弃方案、参考项目的规模（规模不是目标）。

### 7.3 使用流程

1. 明确要参考的问题。
2. 多维度搜索。
3. 筛选可信来源。
4. 抽象成参考卡片（`assets/reference-card-template.md`）。
5. 映射到当前需求。
6. 纳入 draft。
7. 用户审批。
8. 原型/spike/合规审查验证。

停止条件：

- 能回答当前关键设计问题。
- 至少有一个同类、一个局部相似、一个反面/失败案例。
- 多源交叉验证。
- 已抽象出模式，而非复制功能。
- 已识别许可证和法律风险。
- 用户已审批参考方向。

### 7.4 对比评估

目的：

> 把"别人怎么做"转化为"我们该怎么做、不该怎么做、为什么"。

对比单元：目标与场景、架构模式、插件/源接口、数据模型、源发现与更新、缓存/并发/回退、异常与健康检查、权限与安全、合规与许可证、运维与治理、演进路径。

评估维度：需求匹配度、复杂度与实现成本、可维护性与可扩展性、可靠性与异常处理、性能与规模适配、安全/合规/许可证、生态/社区/文档、团队技术栈与能力、交付周期、可逆性与迁移成本、长期演进风险。

证据分级：

- 高：源码、官方文档、架构文档、Release Notes
- 中高：作者复盘、Issue/PR/Discussion、迁移记录
- 中：技术博客、二手分析
- 低：评论、猜测、未经验证总结

输出（对比矩阵见 `assets/comparison-matrix-template.md`）：

- 对比矩阵
- 推荐方案及理由
- 备选方案及触发条件
- 不推荐方案及原因
- 可借鉴模式清单
- 不可借鉴/风险清单
- 待验证清单
- 用户需拍板决策点
- 下一步：原型、spike、合规审查、技术评审

### 7.5 决策规则

- 多独立项目共同模式：强候选，仍需适配。
- 单一项目采用：弱证据，需验证。
- 相反产品也成功：说明非唯一路径。
- 失败案例揭示风险：必须设护栏。
- 许可证不兼容：思想可参考，代码不能抄。
- 合规风险高：单独门禁。
- 无法验证：降级为假设，不能进最终方案。

## 8. 停止条件

满足以下全部时，可停止收集并进入下一阶段：

- 能写出需求草案、范围外清单、验收用例、接口/数据草案。
- 能列出关键假设与风险。
- 高影响不确定项已解决，或已变成经用户批准的假设。
- 有下一步验证或实施计划。
- 用户审批当前基线。
- 关键人工审核门禁已通过。

否则继续收集、验证，或降级为假设。
