# 01 核心原则

## 1. 核心行为原则

### 1.1 先思考再编码

- 不假设、不隐藏困惑、暴露权衡。
- 实现前：陈述假设；不确定就提问；多种解释并列；更简单的方案直说；需求不清就停。
- Agent 计划必须写：假设 / 待确认 / 风险 / 可选方案。
- S 档可简化为一句话假设；M/L 档必须显式。
- 关键假设未确认前，不得进入实现。

### 1.2 简单优先

- 用最少代码解决当前问题，不做投机性设计。
- 不实现未要求的功能；不为一次性代码抽象；不加未要求的灵活性；不为不可能场景写错误处理。
- 可简化，但不得牺牲正确性与可读性。

### 1.3 外科手术式修改

- 只碰必须碰的，只清理自己造成的混乱。
- 不顺手改进相邻代码、注释、格式；不重构没坏的东西。
- 匹配现有风格，即使个人偏好不同。
- 无关死代码只提示，不删除。
- 删除因本次改动不再使用的 import/变量/函数。
- 每行改动都能追溯到用户请求。

> 与"一次成型"的边界：问题域内一次做全，域外只登记不动手，见 `09-execution-protocols.md §3.2`。

### 1.4 目标驱动执行

把任务转成可验证目标：

- 加校验 → 为非法输入写测试，然后让测试通过
- 修 bug → 写复现测试，然后让它通过
- 重构 X → 确保重构前后测试通过

多步任务先给计划：

```text
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

强成功标准让 Agent 独立循环；弱标准需要反复澄清。

## 2. 设计原则

- 组合优先于继承；优先小对象与函数组合。
- 模块化：清晰边界、低耦合、高内聚。
- 单一职责：一个模块/类/函数只做一件事。
- 依赖方向稳定：业务核心不依赖易变细节。
- 接口尽量小，实现可替换。
- 不为"未来可能"提前抽象；真实复用或变化出现后再抽象（前瞻留口见 `09-execution-protocols.md §4.2`）。

## 3. 语言与生态规范

- Java：阿里巴巴 Java 开发手册 + 项目约定。
- Python：PEP 8 / PEP 257 + 项目 lint/format/type 配置。
- JavaScript/TypeScript：项目 ESLint / Prettier / tsconfig。
- Go：Effective Go / gofmt / go vet。
- Rust：rustfmt / clippy。
- SQL、Shell、YAML、Markdown：主流规范 + 项目约定。

优先级：

1. 项目已有约定与工具配置
2. 语言/生态主流规范
3. 本 skill 通用原则

冲突时先指出，再按项目约定执行，除非用户明确要求变更。
本文件不复制具体风格细则：上游规范会变，抄进来只会过期。

## 4. 命名与注释

- 命名说"是什么、做什么"，不说"怎么做"；不用拼音缩写与无意义编号。
- 含义与单位进名字：`timeoutMs`、`sizeBytes`、`retryCount`。
- 布尔量用肯定式（`enabled`，不用 `notDisabled`）。
- 注释写**为什么**（约束、坑、取舍），不写代码复述。
- 不留注释掉的死代码；不要的删掉，历史在 git 里。
- 公开接口的注释写清：能输入什么、返回什么、失败时是什么行为。
